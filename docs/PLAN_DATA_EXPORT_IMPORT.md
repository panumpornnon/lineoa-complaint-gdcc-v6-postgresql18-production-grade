# แผน: ระบบควรมี Export / Import ข้อมูลเป็นไฟล์หรือไม่

> เอกสารนี้เป็น **แผนสำหรับพิจารณา** ยังไม่มีการแก้โค้ดใดๆ ตามเอกสารนี้
> จัดทำ 14 กันยายน 2569

---

## 1. ที่มาของคำถาม

ตลอดการทำงานที่ผ่านมาเจอปัญหาเดิมซ้ำหลายรอบ คือ **ข้อมูลที่เพิ่มผ่านหน้าเว็บอยู่เฉพาะในฐานข้อมูลเครื่องนั้น
ไม่ติดไปกับโค้ด** พอย้ายเครื่องหรือ clone ไปโฟลเดอร์ใหม่ ข้อมูลก็หาย เช่น

- หน่วยงาน กองการเจ้าหน้าที่ ที่เคยเพิ่มไว้ แล้วหายตอนย้ายฐานข้อมูล
- หมวดหมู่ `JOB_RECUITMENT` `REPORT_CORRUPTION` `REPORT_ETHICS` ที่มีเฉพาะใน `complaint_v6_development`
- ข้อมูลเจ้าหน้าที่กองช่าง 10 คน ที่ต้องส่งไฟล์ `.txt` มาแปลงเป็น migration ด้วยมือ

คำถามคือ ควรทำฟีเจอร์ export / import ข้อมูลเป็นไฟล์เข้าไปในระบบเลยไหม

## 2. สิ่งที่มีอยู่แล้ววันนี้

| สิ่งที่มี | ทำอะไร | ครอบคลุมอะไร |
|---|---|---|
| `scripts/backup.sh` | `pg_dump` ทั้งฐานข้อมูล + tar ไฟล์แนบ เก็บย้อนหลัง 14 วัน | ทุกตาราง + ไฟล์รูป |
| `scripts/restore.sh` | `pg_restore` + แตกไฟล์รูปกลับ | ทุกตาราง + ไฟล์รูป |
| `GET /api/admin/reports/export.csv` | ออกรายงานเรื่องร้องเรียนเป็น CSV มี BOM เปิดใน Excel ได้ | เฉพาะ complaints |
| `scripts/export-governance-migration.js` | อ่านหน่วยงาน + หมวดหมู่จากฐานข้อมูล แล้วเขียนเป็นไฟล์ migration | departments, complaint_categories |
| ไฟล์ migration `029` `031` `032` | ข้อมูลอ้างอิงที่เขียนมือ | หน่วยงาน หมวดหมู่ เจ้าหน้าที่กองช่าง |

## 3. หัวใจของเรื่อง: ต้องแยกข้อมูลเป็น 3 กลุ่มก่อน

คำว่า "export / import ข้อมูล" รวมความต้องการ 3 อย่างที่คำตอบไม่เหมือนกันเลยไว้ด้วยกัน
ถ้าไม่แยกก่อน จะออกแบบผิดทั้งระบบ

### กลุ่ม A — ข้อมูลตั้งต้น / ข้อมูลอ้างอิง
หน่วยงาน, หมวดหมู่ + SLA, ข้อมูลเจ้าหน้าที่

- เปลี่ยนไม่บ่อย แต่**ทุกสภาพแวดล้อมต้องเหมือนกัน** (local / สำรอง / GDCC)
- เป็นสิ่งที่ระบบต้องมีตั้งแต่ติดตั้งครั้งแรก ไม่ใช่ข้อมูลที่ผู้ใช้ป้อนระหว่างใช้งาน

### กลุ่ม B — ข้อมูลดำเนินงาน
เรื่องร้องเรียน, ไฟล์แนบ, ประวัติสถานะ, audit log, บัญชีผู้ใช้งาน

- เกิดขึ้นตลอดเวลา แต่ละสภาพแวดล้อม**ไม่ควรเหมือนกัน** (ข้อมูลทดสอบต้องไม่ปนกับข้อมูลจริง)

### กลุ่ม C — การแลกเปลี่ยนข้อมูลกับคน
ออกรายงานให้ผู้บริหาร, รับรายชื่อเจ้าหน้าที่จากกองอื่นเป็น Excel

- เป็นฟีเจอร์สำหรับผู้ใช้ ไม่เกี่ยวกับการย้ายข้อมูลระหว่างเครื่อง

## 4. ข้อเสนอต่อแต่ละกลุ่ม

### กลุ่ม A — ใช้ migration ต่อไป และ **ห้าม** ทำ import เข้าฐานข้อมูลตรงๆ

**คำตอบ: ไม่ควรทำฟีเจอร์ import ไฟล์เข้าฐานข้อมูลผ่านหน้าเว็บ**

เพราะมันจะสร้างปัญหาเดิมซ้ำอีกรอบ — ข้อมูลจะเข้าไปอยู่ในฐานข้อมูลเครื่องเดียว
ไม่ติดไปกับโค้ด แล้วก็หายตอนย้ายเครื่องเหมือนเดิม

**แต่ควรทำ import อีกแบบหนึ่ง:**

> อ่านไฟล์ CSV แล้ว **สร้างไฟล์ migration** ไม่ใช่เขียนลงฐานข้อมูล

```
npm run staff:import -- --department ENGINEERING --file staff-engineering.csv
  → สร้าง sql/0NN_seed_staff_profiles_engineering.sql
```

ผลที่ได้:
- กองอื่นส่ง Excel มา แปลงเป็น CSV แล้วรันคำสั่งเดียว ได้ไฟล์ migration พร้อม review
- ยังผ่านการตรวจสอบด้วยสายตาและผ่าน git ก่อนถึงฐานข้อมูลจริง
- แก้ปัญหาที่กำลังเจ็บอยู่จริงตอนนี้ (ต้องแปลงไฟล์ทีละหน่วยงานด้วยมือ)

**ส่วนที่ควรเพิ่มเติมของเดิม:** `export-governance-migration.js` ยังไม่ครอบคลุม `staff_profiles`
ควรขยายให้รองรับ เพื่อใช้เป็น **เครื่องมือกู้** ในกรณีที่ข้อมูลหลุดเข้าไปอยู่ในฐานข้อมูลแล้ว
ย้ำว่าเป็นเครื่องมือกู้ ไม่ใช่ทางหลักในการทำงานประจำ

---

### กลุ่ม B — ใช้ `pg_dump` ต่อไป **ห้าม** ทำ export/import ระดับแอป

**คำตอบ: ไม่ควรทำ** และมีเหตุผลทางเทคนิคที่หนักแน่น 4 ข้อ

| เหตุผล | รายละเอียด |
|---|---|
| **เลขอ้างอิงจะชนกัน** | `reference_no` มาจาก `complaint_reference_seq` ซึ่งเป็น sequence ของแต่ละฐานข้อมูล การนำเข้าข้ามเครื่องจะได้เลขซ้ำหรือกระโดด |
| **ไฟล์แนบไม่ได้อยู่ในฐานข้อมูล** | รูปอยู่บนดิสก์ที่ `UPLOAD_DIR` การ export เป็น JSON/CSV จะได้แค่ชื่อไฟล์ ไม่ได้ตัวรูป ข้อมูลที่ได้จะไม่ครบและหลอกให้เข้าใจผิดว่าสำรองไว้แล้ว |
| **audit log ต้องเติมอย่างเดียว** | ตาราง `audit_logs` จะเชื่อถือได้ก็ต่อเมื่อไม่มีใครเขียนย้อนหลังได้ การเปิดช่องทาง import ทำลายคุณสมบัตินี้ทันที |
| **รหัสผ่าน** | `staff_users.password_hash` ห้ามหลุดออกจากฐานข้อมูลเด็ดขาด ไม่ว่ารูปแบบใด |

**ช่องว่างที่มีจริงและควรอุด:** `backup.sh` เขียนด้วย shell script รันบน **Windows Server ของ GDCC ไม่ได้**
ควรทำเวอร์ชัน PowerShell (`backup.ps1`) แล้วตั้ง Task Scheduler ให้รันทุกคืน
— เรื่องนี้สำคัญกว่าฟีเจอร์ export/import ใดๆ ที่กล่าวมา เพราะตอนนี้เซิร์ฟเวอร์จริง**ยังไม่มีการสำรองข้อมูลอัตโนมัติเลย**

---

### กลุ่ม C — มีอยู่แล้ว ขยายเพิ่มได้ตามต้องการ

CSV export ของเรื่องร้องเรียนทำงานอยู่แล้ว และมีการบันทึก audit (`report.export.csv`)

สิ่งที่เพิ่มได้ถ้ามีคนขอ:
- ส่งออกเป็น Excel (.xlsx) แทน CSV เพื่อให้จัดรูปแบบคอลัมน์วันที่ได้เอง
- ส่งออกสรุปรายเดือนตามหน่วยงาน สำหรับรายงานผู้บริหาร

ยังไม่มีใครขอ จึงยังไม่ต้องทำ

## 5. สรุปเป็นตารางเดียว

| ความต้องการ | ทำหรือไม่ | วิธีที่ถูกต้อง |
|---|---|---|
| ย้ายหน่วยงาน / หมวดหมู่ / เจ้าหน้าที่ ไปเครื่องอื่น | ✅ มีอยู่แล้ว | ไฟล์ migration ใน `sql/` |
| แปลงรายชื่อเจ้าหน้าที่จาก Excel เป็น migration | ✅ **ควรทำ** | สคริปต์ CLI สร้างไฟล์ migration |
| กู้ข้อมูลอ้างอิงที่หลุดเข้าไปอยู่ในฐานข้อมูลแล้ว | ⚠️ มีบางส่วน | ขยาย `export-governance-migration.js` ให้ครอบ `staff_profiles` |
| สำรอง / กู้คืนทั้งระบบ | ⚠️ มี แต่ใช้บน GDCC ไม่ได้ | ทำ `backup.ps1` + Task Scheduler |
| import เรื่องร้องเรียนข้ามเครื่อง | ❌ **ไม่ควรทำ** | ใช้ `pg_restore` เท่านั้น |
| import ข้อมูลอ้างอิงเข้าฐานข้อมูลผ่านหน้าเว็บ | ❌ **ไม่ควรทำ** | สร้าง migration แทน |
| ออกรายงานให้ผู้บริหาร | ✅ มีอยู่แล้ว | `GET /reports/export.csv` |

## 6. ลำดับที่แนะนำ ถ้าจะลงมือทำ

1. **`backup.ps1` + Task Scheduler บน GDCC** — เร่งด่วนที่สุด เพราะตอนนี้ยังไม่มีการสำรองอัตโนมัติ
2. **สคริปต์แปลง CSV → migration ของ staff_profiles** — แก้ความเจ็บที่เกิดขึ้นจริงทุกครั้งที่มีกองใหม่ส่งรายชื่อมา
3. **ขยาย `export-governance-migration.js` ให้ครอบ `staff_profiles`** — เป็นตาข่ายรองรับ
4. **ทดสอบ `restore.sh` จริงสักครั้ง** — backup ที่ไม่เคยกู้คืนสำเร็จ ไม่ต่างจากไม่มี backup

ข้อ 1 กับ 4 ไม่ใช่ฟีเจอร์ แต่เป็นสิ่งที่ต้องมีก่อนระบบเปิดใช้จริง

## 7. ข้อควรระวังเรื่องข้อมูลส่วนบุคคล

ไฟล์ที่ส่งออกจากระบบนี้มีข้อมูลส่วนบุคคลทั้งของเจ้าหน้าที่และประชาชน
(ชื่อ–สกุล, เบอร์โทรศัพท์, ไอดีไลน์, ตำแหน่งที่แจ้งเหตุ)

- **ห้าม commit ไฟล์ CSV ต้นฉบับเข้า git** — ควรเพิ่ม `*.csv` ในโฟลเดอร์นำเข้าลง `.gitignore`
- ไฟล์ migration ที่มีรายชื่อเจ้าหน้าที่จะอยู่ใน git ถาวร — เป็นข้อมูลที่เผยแพร่ในทำเนียบราชการอยู่แล้ว จึงยอมรับได้ แต่ต้องรู้ตัวว่าลบออกจากประวัติ git ไม่ได้
- ทุกการส่งออกควรบันทึก audit log ว่าใครเป็นคนสั่ง (`/reports/export.csv` ทำแล้ว ถ้าเพิ่มช่องทางใหม่ต้องทำด้วย)
- ไฟล์สำรองฐานข้อมูลต้องตั้งสิทธิ์ให้อ่านได้เฉพาะผู้ดูแลระบบ (`backup.sh` ใช้ `umask 077` อยู่แล้ว เวอร์ชัน PowerShell ต้องทำเทียบเท่า)

# ภาคผนวก: วิธีทำสำหรับ "ข้อมูลหลังบ้านที่เพิ่มเข้ามาทีหลัง"

> ส่วนนี้ลงรายละเอียดเฉพาะกลุ่ม A ซึ่งเป็นโจทย์จริงที่ต้องแก้
> ไม่เกี่ยวกับเรื่องร้องเรียนและไฟล์แนบ

## A1. ขอบเขต — ตารางไหนใช่ ตารางไหนไม่ใช่

| ตาราง | อยู่ในขอบเขต | เหตุผล |
|---|---|---|
| `departments` | ✅ | ข้อมูลอ้างอิง มี `code` เป็นกุญแจที่ข้ามเครื่องได้ |
| `complaint_categories` | ✅ | เช่นเดียวกัน รวม `sla_hours` และ `sort_order` |
| `staff_profiles` | ✅ | ทำเนียบเจ้าหน้าที่ ไม่ใช่บัญชีเข้าระบบ ไม่มีรหัสผ่าน |
| `staff_users` | ❌ | มี `password_hash` ห้ามส่งออกเด็ดขาด บัญชีต้องสร้างแยกในแต่ละเครื่องด้วย `npm run admin:create` |
| `complaints` และตารางลูก | ❌ | ข้อมูลดำเนินงาน ใช้ `pg_dump` |
| `audit_logs` | ❌ | ต้องเติมอย่างเดียวจึงจะเชื่อถือได้ |

## A2. ปัญหาที่แท้จริงไม่ใช่ "ส่งออกไม่ได้" แต่คือ "ไม่มีใครรู้ว่ามีอะไรเปลี่ยน"

ทุกวันนี้ถ้าผู้ดูแลเพิ่มหน่วยงานใหม่ผ่านหน้าเว็บบน GDCC **ไม่มีสัญญาณใดๆ บอกเลย**
ว่าฐานข้อมูลกับโค้ดเริ่มไม่ตรงกันแล้ว กว่าจะรู้ตัวก็ตอนย้ายเครื่องแล้วข้อมูลหาย

ดังนั้นเครื่องมือที่ต้องมีไม่ใช่แค่ "ส่งออก" แต่มี 3 ชิ้น

| เครื่องมือ | หน้าที่ | สถานะ |
|---|---|---|
| `db:migrate` | นำไฟล์เข้าฐานข้อมูล — นี่คือ "import" ที่ถูกต้อง | ✅ มีแล้ว |
| `db:export-governance` | อ่านฐานข้อมูล เขียนเป็นไฟล์ migration | ⚠️ มีแล้ว แต่ยังไม่ครอบ `staff_profiles` |
| `db:check-governance` | **เทียบฐานข้อมูลกับไฟล์ แล้วเตือนว่ามีอะไรที่ยังไม่อยู่ในโค้ด** | ❌ ยังไม่มี — นี่คือชิ้นที่ขาดจริงๆ |

### `db:check-governance` ควรทำอะไร

รันแล้วบอกว่า

```
ตรวจสอบข้อมูลหลังบ้าน เทียบฐานข้อมูลกับไฟล์ใน sql/

หน่วยงาน          : 7 รายการ  ✅ ตรงกับโค้ดทั้งหมด
หมวดหมู่           : 11 รายการ ⚠️ มี 1 รายการที่ไม่มีในโค้ด
                      - PARK_MAINTENANCE (ดูแลสวนสาธารณะ)
ข้อมูลเจ้าหน้าที่   : 18 คน     ⚠️ มี 8 คนที่ไม่มีในโค้ด
                      - กองสาธารณสุขและสิ่งแวดล้อม 8 คน

แนะนำ: รัน npm run db:export-governance แล้ว commit ไฟล์ที่ได้
```

เอาไปใส่ใน checklist ก่อน deploy ทุกครั้ง หรือรันเป็นงานประจำเดือน
เท่านี้ก็ไม่มีทางที่ข้อมูลจะหายแบบที่ผ่านมาอีก

## A3. ขั้นตอนการทำงานประจำที่แนะนำ

เลือกโหมดใดโหมดหนึ่ง แล้วยึดโหมดนั้น อย่าสลับไปมา

### โหมด 1 — โค้ดเป็นต้นทาง (เข้มงวด)

ห้ามเพิ่มข้อมูลหลังบ้านผ่านหน้าเว็บบนเครื่องจริง ทุกการเปลี่ยนแปลงต้องผ่าน
เขียน migration → git → deploy → `db:migrate`

- **ดี:** ทุกเครื่องเหมือนกันเสมอ มีประวัติใน git ครบ ตรวจทานได้ก่อนขึ้นจริง
- **เสีย:** เพิ่มหน่วยงานหนึ่งหน่วยต้อง deploy หนึ่งรอบ ช้าเกินไปสำหรับงานประจำวัน

### โหมด 2 — ฐานข้อมูลเป็นต้นทาง แล้วส่งออกกลับ (แนะนำ)

ผู้ดูแลเพิ่มผ่านหน้าเว็บได้ตามปกติ แล้วมีรอบการส่งออกกลับเข้าโค้ด

1. บนเครื่อง GDCC — `git pull` ก่อน เพื่อให้เลขไฟล์ล่าสุดตรงกัน
2. `npm run db:export-governance` → ได้ `sql/0NN_sync_governance_data.sql`
3. เปิดไฟล์อ่านด้วยตา ตรวจว่าไม่มีข้อมูลแปลกปลอม
4. `git add` + `commit` + `push`
5. เครื่องอื่น `git pull` แล้ว `npm run db:migrate`

**ควรทำรอบนี้เมื่อไร:** ทุกครั้งที่เพิ่มหน่วยงานหรือทำเนียบเจ้าหน้าที่ชุดใหม่
และบังคับทำก่อน deploy ทุกครั้ง

## A4. ปัญหาที่ต้องแก้ก่อนโหมด 2 จะใช้งานได้จริง

### ปัญหา 1 — เลขไฟล์ชนกัน

`export-governance-migration.js` ตั้งเลขจาก "ไฟล์ล่าสุด + 1" ถ้า GDCC สร้าง `033`
พร้อมกับที่เครื่อง dev ก็สร้าง `033` จะได้ไฟล์คนละเนื้อหาเลขเดียวกัน แล้ว merge ชนกัน

**ทางแก้:** ต้อง `git pull` ก่อนรันเสมอ (ใส่ในขั้นตอนแล้ว) และให้สคริปต์
เตือนถ้าตรวจพบว่า working tree มีไฟล์ `.sql` ที่ยังไม่ commit

### ปัญหา 2 — `staff_profiles` ไม่มีรหัสประจำตัว

`departments` และ `complaint_categories` มีคอลัมน์ `code` ที่ข้ามเครื่องได้
แต่ `staff_profiles` ไม่มี ต้องใช้ **ชื่อ–สกุล + หน่วยงาน** เป็นตัวระบุแทน
(วิธีเดียวกับที่ไฟล์ `032` ใช้อยู่)

ผลคือถ้าเจ้าหน้าที่เปลี่ยนชื่อ–สกุล ระบบจะมองเป็นคนใหม่ และถ้ามีคนชื่อซ้ำกัน
ในหน่วยงานเดียวกันจะแยกไม่ออก

**ทางเลือก:** เพิ่มคอลัมน์ `employee_code` แบบไม่บังคับกรอก ใครกรอกก็ใช้เป็นตัวระบุ
ใครไม่กรอกก็ใช้ชื่อ–สกุลไปก่อน — เป็นการแก้ที่ต้นเหตุ แต่ต้องเพิ่ม migration
และเพิ่มช่องในหน้าจอด้วย ยังไม่จำเป็นตอนนี้ ทำเมื่อเริ่มเจอปัญหาจริง

### ปัญหา 3 — ไฟล์ที่ส่งออกไม่ลบข้อมูล

สคริปต์ใช้ `ON CONFLICT DO UPDATE` เท่านั้น ไม่มีคำสั่งลบ ตั้งใจให้เป็นแบบนี้
เพื่อไม่ให้ข้อมูลของสภาพแวดล้อมอื่นหายโดยไม่ตั้งใจ

ผลข้างเคียง: ถ้าลบหน่วยงานออกจาก GDCC ผ่านหน้าเว็บ เครื่องอื่นจะยังมีอยู่
**การลบต้องเขียน migration แยกด้วยมือทุกครั้ง** ซึ่งเหมาะสมแล้ว เพราะการลบ
ข้อมูลอ้างอิงเป็นการกระทำที่ควรผ่านการตรวจทาน
