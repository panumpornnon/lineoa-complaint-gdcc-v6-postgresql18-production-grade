# แผนรับมือเหตุฉุกเฉินและการกู้คืนระบบ

> **เอกสารแผนสำหรับพิจารณา ยังไม่มีการแก้ไขโค้ดใดๆ ตามเอกสารนี้**
> จัดทำ 28 กันยายน 2569

---

## 1. สรุปสิ่งที่มีและไม่มีในวันนี้

| ความสามารถ | สถานะ | หมายเหตุ |
|---|---|---|
| สำรองฐานข้อมูล + ไฟล์รูป | ⚠️ มีสคริปต์ แต่ใช้ไม่ได้ | `scripts/backup.sh` เป็น shell รันบน Windows Server ไม่ได้ |
| กู้คืนจากไฟล์สำรอง | ⚠️ เช่นเดียวกัน | `scripts/restore.sh` |
| สำรองอัตโนมัติตามเวลา | ❌ ไม่มี | ต้องมีคนกดเอง |
| ทดสอบว่ากู้คืนได้จริง | ❌ ไม่เคยทำ | |
| ย้ายระบบไปเครื่องใหม่ | ⚠️ ทำได้ แต่ไม่มีเอกสาร | อาศัยความจำของผู้ทำ |
| ตั้งรหัสผ่านใหม่ให้เจ้าหน้าที่ | ✅ มี | หน้าจัดการผู้ใช้งาน / นำเข้า CSV / คำสั่ง admin:create |
| ผู้ใช้กดลืมรหัสผ่านเอง | ❌ ไม่มี | ตารางบัญชีไม่มีคอลัมน์อีเมล |
| ปลดเซสชันให้ผู้ใช้ที่ติดค้าง | ❌ ไม่มี | ต้องรอครบ 60 นาที |

**ข้อสรุปที่สำคัญที่สุดของเอกสารนี้:** เซิร์ฟเวอร์ GDCC ที่ประชาชนใช้งานอยู่จริง
**ยังไม่มีการสำรองข้อมูลอัตโนมัติเลยแม้แต่ครั้งเดียว** หากดิสก์เสียหรือมีคนลบผิดในวันนี้
เรื่องร้องเรียนทั้งหมดที่ประชาชนส่งเข้ามาจะหายถาวร กู้คืนไม่ได้

## 2. เหตุการณ์ที่ต้องรับมือ เรียงตามความเสี่ยงจริง

| # | เหตุการณ์ | โอกาสเกิด | ความเสียหาย | พร้อมรับมือ |
|---|---|---|---|---|
| 1 | ข้อมูลสูญหาย (ดิสก์เสีย ลบผิด ติดไวรัส) | ต่ำ | **สูงมาก — กู้ไม่ได้เลย** | ❌ |
| 2 | เจ้าหน้าที่ลืมรหัสผ่าน | **สูงมาก** | ต่ำ | ✅ |
| 3 | เจ้าหน้าที่ติดค้างเพราะลืมออกจากระบบ | **สูง** | ต่ำ แต่กวนใจทุกวัน | ⚠️ รอ 60 นาที |
| 4 | ต้องย้ายระบบไปเครื่องใหม่ | ต่ำ | กลาง | ⚠️ ไม่มีเอกสาร |
| 5 | บัญชี DEV ลืมรหัสผ่านพร้อมกันทุกคน | ต่ำมาก | **สูง — เข้าระบบไม่ได้เลย** | ⚠️ ต้องเข้าเครื่อง |

**อ่านตารางนี้อย่างไร:** แถวที่ 1 ความเสียหายสูงสุดและยังไม่มีอะไรรองรับเลย
จึงเป็นงานที่ต้องทำก่อนเรื่องอื่นทั้งหมด ส่วนแถวที่ 2 และ 3 เกิดบ่อยแต่เสียหายน้อย
และมีทางแก้อยู่แล้ว จึงไม่เร่งด่วนเท่า

## 3. การสำรองข้อมูลประจำ — งานที่ต้องทำก่อนเรื่องอื่น

### สิ่งที่ต้องสำรอง มี 2 ก้อน ไม่ใช่ก้อนเดียว

| ก้อน | อยู่ที่ไหน | สำรองด้วย |
|---|---|---|
| ฐานข้อมูล | PostgreSQL | `pg_dump --format=custom` |
| **รูปภาพที่ประชาชนแนบมา** | โฟลเดอร์ `uploads\` บนดิสก์ | บีบอัดเป็น zip |

⚠️ **จุดที่พลาดกันบ่อยที่สุด** — รูปภาพไม่ได้อยู่ในฐานข้อมูล ถ้าสำรองแต่ฐานข้อมูล
แล้วกู้คืน จะได้เรื่องร้องเรียนครบทุกเรื่องแต่รูปหายหมด ซึ่งเป็นหลักฐานสำคัญของงานร้องเรียน

### ข้อเสนอ

สร้าง `scripts/windows/backup.cmd` ทำสามอย่างในไฟล์เดียว

1. `pg_dump` ฐานข้อมูลเป็นไฟล์ `.dump` ตั้งชื่อตามวันเวลา
2. บีบอัดโฟลเดอร์ `uploads\` เป็น zip ชื่อเดียวกัน
3. ลบไฟล์สำรองที่เก่าเกิน 14 วันออกอัตโนมัติ

แล้วตั้ง **Task Scheduler** ให้รันทุกคืน เวลาที่ไม่มีคนใช้งาน

### เรื่องที่ต้องตัดสินใจเพิ่ม

- **เก็บไว้ที่ไหน** — เก็บไว้ดิสก์เดียวกับฐานข้อมูลไม่ช่วยอะไรถ้าดิสก์เสีย
  ควรมีปลายทางที่สอง เช่นไดรฟ์อื่น เครื่องอื่นในวง หรือที่เก็บของ GDCC
- **สิทธิ์การเข้าถึง** — ไฟล์สำรองมีข้อมูลส่วนบุคคลของประชาชนครบถ้วน
  ต้องจำกัดให้อ่านได้เฉพาะผู้ดูแลระบบ
- **เก็บย้อนหลังนานเท่าไร** — 14 วันเป็นค่าตั้งต้น ถ้าระเบียบของเทศบาลกำหนดไว้ต่างจากนี้ให้ยึดตามระเบียบ

### และต้องทดสอบกู้คืนจริงอย่างน้อยหนึ่งครั้ง

ไฟล์สำรองที่ไม่เคยกู้คืนสำเร็จ ไม่ต่างจากไม่มีไฟล์สำรอง
ควรทดสอบกู้ลงฐานข้อมูลชื่ออื่นบนเครื่องเดียวกัน แล้วเปิดดูว่าข้อมูลครบและรูปเปิดได้

## 4. ขั้นตอนย้ายระบบไปเครื่องใหม่

### ที่เครื่องเดิม

1. หยุด service เพื่อไม่ให้มีข้อมูลเข้าใหม่ระหว่างสำรอง
2. `pg_dump --format=custom` ฐานข้อมูล
3. บีบอัดโฟลเดอร์ `uploads\`
4. คัดลอกไฟล์ `.env` ไว้เป็นต้นแบบ

### ที่เครื่องใหม่

1. ติดตั้ง PostgreSQL 18 และ Node 22 ขึ้นไป
2. สร้างฐานข้อมูลและผู้ใช้ฐานข้อมูล
3. `pg_restore --no-owner --no-privileges`
4. วางโค้ด และแตกไฟล์ `uploads\` กลับที่เดิม
5. แก้ `.env` — `DATABASE_URL`, `CORS_ORIGINS`, `UPLOAD_DIR` ต้องเป็นค่าของเครื่องใหม่
6. `npm ci`
7. `npm run db:migrate` — ควรข้ามทุกไฟล์เพราะตาราง `schema_migrations` ติดมากับ dump แล้ว
8. `npm run db:check-governance` — ยืนยันว่าข้อมูลหลังบ้านครบ
9. ติดตั้ง Windows Service และเปิดกฎไฟร์วอลล์
10. **แก้ Webhook URL ใน LINE Developers Console ให้ชี้เครื่องใหม่**

### สามจุดที่ต้องระวังเป็นพิเศษ

**ก. ค่า checksum ของไฟล์ migration**
หากเครื่องใหม่ `git clone` แล้วไฟล์ `.sql` ถูกแปลงการขึ้นบรรทัดเป็นแบบ Windows
จะขึ้นข้อความว่าไฟล์ถูกแก้หลังถูกใช้งานแล้ว และหยุดทั้งชุด
โปรเจกต์มีกฎ `*.sql text eol=lf` ใน `.gitattributes` ป้องกันไว้แล้ว
แต่ถ้าคัดลอกไฟล์ด้วยวิธีอื่นก็ต้องระวังเช่นกัน

**ข. ทุกคนจะหลุดจากระบบ**
ตาราง `staff_sessions` ย้ายมาด้วย แต่ token ที่ผู้ใช้ถืออยู่ชี้ไปเซสชันเดิม
ทุกคนต้องเข้าสู่ระบบใหม่ ซึ่งถูกต้องแล้วและไม่ต้องแก้อะไร

**ค. สิ่งที่ไม่ได้อยู่ในฐานข้อมูล ต้องย้ายมือทั้งหมด**
ไฟล์รูป, `.env`, Windows Service, กฎไฟร์วอลล์, Webhook URL ของ LINE

### ใช้ pgAdmin แทนคำสั่งได้ไหม

ได้ ทั้งสองอย่างคือหน้าจอที่ห่อ `pg_dump` / `pg_restore` ไว้อีกที
ตอนสำรองให้เลือก Format เป็น **Custom** และติ๊ก "Do not save owner" กับ "Do not save privileges"
ไม่งั้นตอนกู้คืนจะฟ้องว่าไม่มีผู้ใช้ชื่อเดิมในระบบ

ข้อควรรู้: หากขึ้นว่าหา `pg_dump` ไม่เจอ ให้ตั้งที่
`File → Preferences → Paths → Binary paths` ชี้ไป `C:\Program Files\PostgreSQL\18\bin`

**แต่ pgAdmin ทำงานประจำวันแทนไม่ได้** เพราะต้องมีคนนั่งกด และไม่ย้ายโฟลเดอร์รูปให้
เหมาะกับงานที่ทำเป็นครั้งคราว เช่นตอนย้ายเครื่องจริง

## 5. การกู้บัญชีเมื่อลืมรหัสผ่าน

ระบบไม่มีช่องทางให้ผู้ใช้กดลืมรหัสผ่านเอง เพราะตาราง `staff_users` ไม่มีคอลัมน์อีเมล
จึงส่งลิงก์ตั้งรหัสใหม่ไม่ได้ ทุกกรณีต้องให้ผู้ดูแลตั้งให้

| กรณี | วิธีแก้ | ต้องเข้าเครื่องเซิร์ฟเวอร์ไหม |
|---|---|---|
| เจ้าหน้าที่ทั่วไปลืม | หน้าจัดการผู้ใช้งาน กดแก้ไขแล้วกรอกรหัสใหม่ | ไม่ต้อง |
| ลืมพร้อมกันหลายคน | ส่งออก CSV กรอกรหัสในคอลัมน์ password เฉพาะแถวที่ต้องการ แล้วนำเข้ากลับ | ไม่ต้อง |
| บัญชี DEV ลืม | คำสั่ง `npm run admin:create` ด้วย username เดิม | **ต้อง** |

### ทางกันไว้ล่วงหน้า

ระบบอนุญาตให้มีบัญชี DEV ได้หลายบัญชีแล้ว (จาก migration 030)
**ควรสร้างไว้อย่างน้อย 2 บัญชี ให้คนละคนถือ** จะได้ไม่ต้องพึ่งการเข้าเครื่องเซิร์ฟเวอร์ทุกครั้ง
และไม่ติดขัดเมื่อผู้ดูแลคนเดียวลาหรือลาออก

### ทางเลือกหากต้องการระบบรีเซ็ตอัตโนมัติในอนาคต

| ทาง | ความเห็น |
|---|---|
| ส่งรหัสใหม่ทาง LINE | เหมาะที่สุด เพราะระบบผูกกับ LINE OA อยู่แล้วและ `staff_profiles` เก็บ LINE ID ครบ แต่ต้องผูกบัญชีเข้าระบบกับโปรไฟล์ก่อน ซึ่งตอนนี้ยังเป็นคนละตาราง |
| ส่งอีเมล | ต้องเพิ่มคอลัมน์อีเมล ตั้งค่า SMTP ของเทศบาล และจัดการ token หมดอายุ |
| ให้ผู้ดูแลตั้งให้ (ปัจจุบัน) | เหมาะกับองค์กรที่เจ้าหน้าที่นั่งอยู่ตึกเดียวกันและโทรหากันได้ |

**ข้อเสนอ:** ยังไม่ต้องทำ การเพิ่มช่องทางรีเซ็ตอัตโนมัติเพิ่มพื้นที่โจมตีมากกว่าเพิ่มความสะดวก
สำหรับหน่วยงานขนาดนี้

## 6. เจ้าหน้าที่ติดค้างเพราะลืมออกจากระบบ

ระบบอนุญาตให้ใช้งานได้ครั้งละหนึ่งเครื่อง เซสชันจะว่างลงได้สามทาง

| ทาง | ใช้เวลา |
|---|---|
| กดออกจากระบบ | ทันที |
| ปิดเบราว์เซอร์ หรือ Shut down ปกติ | ประมาณ 15 วินาที |
| ไฟดับ เครื่องค้าง หรือปิดกระบวนการด้วยกำลัง | **60 นาที** |

แถวสุดท้ายคือกรณีที่ยังไม่มีทางลัด เพราะไม่มีโค้ดใดทำงานเพื่อส่งสัญญาณบอกเซิร์ฟเวอร์

**ข้อเสนอ:** ทำหน้าให้ผู้ดูแลเห็นว่าใครกำลังใช้งานอยู่ พร้อมปุ่มบังคับออกจากระบบ
ข้อมูลที่ต้องใช้เก็บครบอยู่แล้วในตาราง `staff_sessions` ได้แก่ ชื่อผู้ใช้ หมายเลขไอพี
ข้อมูลเบราว์เซอร์ เวลาเข้าสู่ระบบ และเวลาใช้งานล่าสุด เหลือเพียงทำหน้าจอ

ได้ประโยชน์สองต่อ คือปลดให้เจ้าหน้าที่ที่ติดค้างได้ทันที
และผู้ดูแลเห็นภาพว่ามีใครใช้งานระบบอยู่บ้างในขณะนั้น

## 7. ช่องโหว่ที่พบระหว่างตรวจสอบ

**การเปลี่ยนรหัสผ่านจากหน้าจัดการผู้ใช้งาน ไม่ได้ยกเลิกเซสชันเดิม**

เส้นทาง `PATCH /governance/users/:id` เขียนค่า `password_hash` ใหม่แล้วจบ
ไม่ได้แตะตาราง `staff_sessions` เลย

ผลคือหากเปลี่ยนรหัสผ่านเพราะสงสัยว่ารหัสรั่ว ผู้ที่ได้รหัสเดิมไปยังใช้งานต่อได้
จนกว่า token จะหมดอายุ ซึ่งขัดกับเหตุผลที่เปลี่ยนรหัสตั้งแต่แรก

น่าสังเกตว่า**ช่องทางนำเข้าไฟล์ CSV ทำถูกต้องอยู่แล้ว** แต่หน้าจัดการผู้ใช้งาน
ซึ่งเป็นช่องทางที่ใช้บ่อยกว่ากลับไม่ได้ทำ

**ขนาดงาน:** เพิ่มประมาณสิบบรรทัดในเส้นทางเดียว

## 8. ลำดับที่แนะนำ

| # | งาน | เหตุผล |
|---|---|---|
| 1 | `backup.cmd` + Task Scheduler บน GDCC | ความเสี่ยงเดียวที่ความเสียหายกู้คืนไม่ได้ และยังไม่มีอะไรรองรับเลย |
| 2 | ทดสอบกู้คืนจริงหนึ่งครั้ง | พิสูจน์ว่าข้อ 1 ใช้ได้จริง ไม่ใช่แค่สร้างไฟล์ได้ |
| 3 | แก้ให้การเปลี่ยนรหัสผ่านยกเลิกเซสชันเดิม | งานเล็กมาก แต่ปิดช่องโหว่ด้านความปลอดภัย |
| 4 | สร้างบัญชี DEV สำรองอีกหนึ่งบัญชี | ไม่ต้องเขียนโค้ด แค่รันคำสั่งเดียว |
| 5 | หน้าดูเซสชัน + ปุ่มบังคับออกจากระบบ | แก้เรื่องกวนใจประจำวัน |
| 6 | `docs/MIGRATE_SERVER.md` แบบมีช่องติ๊ก | ใช้ตอนย้ายเครื่องจริง ซึ่งยังไม่เกิด |

ข้อ 1 ถึง 4 รวมกันใช้เวลาไม่มาก และปิดความเสี่ยงที่หนักที่สุดได้ทั้งหมด

### ไม่ทำช่องทางอัปโหลดไฟล์ .sql เข้าไปรันผ่านหน้าเว็บ

แม้จะจำกัดว่ารับเฉพาะไฟล์ที่มีแต่ข้อมูล ก็ยังไม่ปลอดภัย ด้วยเหตุผลสามข้อ

1. **พิสูจน์ไม่ได้ว่ามีแต่ข้อมูลจริง** การค้นหาคำต้องห้ามหลบได้ด้วยคอมเมนต์คั่นกลาง
   หรือการต่อสตริง จะตรวจให้ถูกต้องต้องใช้ตัวแยกไวยากรณ์ SQL เต็มรูปแบบ
2. **คำสั่งที่อันตรายที่สุดไม่ใช่คำสั่งเปลี่ยนโครงสร้าง** คำสั่ง `COPY ... FROM PROGRAM`
   เป็นคำสั่งจัดการข้อมูล แต่สั่งรันคำสั่งบนเครื่องเซิร์ฟเวอร์ได้
3. **คำสั่งเพิ่มข้อมูลล้วนก็ยึดระบบได้** เพิ่มแถวในตารางบัญชีผู้ใช้พร้อมสิทธิ์สูงสุด
   เขียนบันทึกการตรวจสอบปลอม หรือใช้ `ON CONFLICT DO UPDATE` แก้ข้อมูลเดิม

**ทางที่ใช้แทน:** ไฟล์ migration วางในโฟลเดอร์ `sql\` แล้วสั่ง `npm run db:migrate`
หรือ dump ข้อมูลกู้คืนด้วย `psql` บนเครื่อง ทั้งสองทางต้องมีคนที่เข้าถึงเครื่องเซิร์ฟเวอร์
เป็นคนสั่ง ไม่ใช่ใครก็ตามที่ล็อกอินหน้าเว็บด้วยบัญชีผู้ดูแล ซึ่งเป็นเส้นแบ่งความปลอดภัยที่สำคัญ

## 10. เรื่องที่ยังต้องตัดสินใจ
